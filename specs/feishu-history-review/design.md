# 飞书历史回顾（feishu-history-review）——brainstorming 方向性设计

> **产出方式声明**：standalone `brainstorming` 技能未安装于本机技能分发目录（`~/.zcode/skills/` 无此项），
> 本文件按用户级 AGENTS.md「brainstorming 覆盖规则」直接执行，章节限定与禁止事项以该文件为准。
> 分级：**L 级**（跨拉取 / AI 判定 / UI / 统计口径的多层新能力）。

## ① 问题理解

**要解决什么**：

1. 收音机当前只覆盖「装应用、开轮询之后」的消息（首次回看 24h）——安装前几个月消息里的任务脉络完全不可见。
2. AI 判定只有四动作（todo / update / followUp / none），全部面向「需要本人行动」的未完成待办；历史消息里大量任务的**结局已经发生**（完成 / 搁置 / 取消），没有出口表达「已完成的、带跟进记录的待办」。
3. 用户诉求：一次性拉取几个月飞书消息做分析，梳理过去一段时间的任务完成情况。

**谁**：已跑通收音机链路的存量用户——新装用户想补齐历史、老用户想做季度或更长周期的复盘。

**为什么**：

- 「图鉴 = 成就记录」的世界观下，只有当天捕捉的图鉴是残缺的；任务的可信图景需要历史纵深。
- 与既有方向同轴：每周复盘向导（ReviewWizard）、Roadmap 的任务时间线、摘要式审查（digest）、52 周热力图。
- 迁移场景真实存在：从其他工具转来的用户，历史任务的第一手记录就在 IM 里。

**success criteria**（方向性）：

1. 用户能选定时间范围（如近 3 个月）显式触发一次性历史拉取；过程可中止、可续跑、进度可见。
2. 对「过去一段时间做了什么、每件事跟到哪、结局如何」产出一份可读回顾，每项判定附证据消息与置信度。
3. 用户可把回顾中的事项选择性收录为「已完成的、带跟进记录的」待办；收录**不污染**游戏化统计（连胜 / 里程碑 / 今日捕捉）。
4. 全程复用假名化与「AI 建议、人确认」边界；人工确认工作量与价值相称（不出现几百张待确认卡的瘫痪态）。

## ② 关键约束

- **产品哲学硬约束**：
  - 注意力友好——回填是重操作，必须用户显式触发、随时可停、失败不轰炸；
  - 宁漏勿滥——历史「结局判定」的误报直接污染图鉴统计，错误代价不对称比增量场景更深；
  - 只做正向激励——回填不得制造虚假连胜 / 里程碑贺词；
  - AI 建议、人确认——followUp 式免确认直写在回填场景**禁用**。
- **本地优先与隐私**：数月历史消息全量送所配置 agent（假名化链路已有），量级放大后隐私边界须在触发前显式告知。
- **成本护栏**：数月消息 ≈ 数千条判定、数百次 agent 无头调用的量级；时长与 token 成本要可预估、可中止（聚合降批是方向，不是定论）。
- **既有资产复用边界**：拉取（时间窗分页）、tools 判定链路、假名化、建议-分诊、chat_feedback 飞轮全部复用；判重上下文（`pk context` 只列未完成待办）是已知缺口；**60 天清理按 `chat_messages.created_at` 判龄，而该列写入的是消息发送时间（`sent_rfc3339`）——回填的历史消息入库即满足删除条件，会被下一轮增量清理立即删掉**，清理豁免/口径调整是本次的直接依赖（SDD §8 已列为必改面）。
- **反 drive-by**：统计隔离必须触碰连胜 / 图鉴口径（`completed_at` 日期集合），属本次改动的直接依赖，允许动；但不顺手重构无关链路。

## ③ 方案探索

### 方案 A：逐条回填——现有管道直接拉长

把历史窗口切段重放现有管道：拉取 → needs_ai 过滤 → 逐条判定（新增 done 动作）→ 建议卡 → 收音机分诊（加回填分区）。

- **优点**：链路 100% 复用，改动最小；判定粒度与现状一致，用户心智零迁移。
- **缺点**：
  - 同一件事在历史里天然多轮出现（布置 → 催 → 交付 → 确认），逐条判定会生成一堆指向同一事项的建议；现有三道判重防线全部为「未完成清单」设计，历史聚合场景失效。
  - 「结局」判定需要跨消息证据链（我回复做完了 / 对方确认收到），单条消息视角天然不可见，判定质量是三方案里最差的。
  - 数百张建议卡压垮收音机的逐条分诊交互；确认工作量与「梳理」目的不成比例。
  - token / 时长成本最高（同一会话上下文反复随条送审）。

### 方案 B：回顾报告先行，收录可选（**推荐**）

回填拉取后不逐条判定：先按会话 / 时间把消息聚合成「事件簇」，AI 对每簇产出**生命周期判定**（事项、时间线、结局、证据消息、置信度），渲染为一份回顾报告；用户在报告上逐项操作——「收录为已完成待办（带跟进记录）/ 收录为未完成待办 / 忽略」。

- **优点**：
  - 判定单位从「消息」升到「事件」，与「梳理完成情况」的目的对齐；证据链成为判定输入的自然结构而非障碍。
  - 人工确认从几百张卡变成滚动审阅一份报告；报告本身即交付物——即使一项都不收录，「梳理」的价值也已达成。
  - 批次数比逐条降约一个量级，成本可控。
  - 给方案 A 留了退路：报告逐项收录本质上就是「以事件为单位的建议卡」，极端场景可退化逐条处理。
- **缺点**：新增「聚合 + 报告 + 收录」三个环节，工程量为三方案最大；报告与收录是新 UI 面（可借 ReviewWizard 的向导形态先例）；事件簇的聚合质量决定一切，聚合错了需要人工拆并。

### 方案 C：纯回顾报告，不回写任务库

同 B 的聚合判定，但止步于生成一份回顾文档（现有「导出日报 Markdown」的放大版），不提供收录为待办的出口。

- **优点**：最轻——不动任务模型、不碰统计口径、无确认流；隐私面最小。
- **缺点**：不满足用户点名诉求（已完成的、带跟进记录的待办）；回顾结论无法沉淀进图鉴 / 时间线，下次回顾重复拉、重复判、重复付费；报告与任务库两个真相源割裂。

### 推荐：方案 B

A 的两个失败模式（重复卡海 + 结局判定失真）恰好砸在需求的核心价值上；C 直接割掉用户点名要的出口。B 的额外工程量集中在报告 / 收录 UI，后端管道三方案差异不大——**用 UI 工程量换判定质量与确认效率**，方向上值得。

**方向性边界**（留给 SDD / AD，不在本文定论）：事件簇的聚合粒度与算法形态、报告的渲染载体、done 收录的协议形态（新 action vs todo 扩展字段）、回填拉取的并发与断点策略。

## ④ 待落地清单（交给 SDD / AD 的开放项）

1. **done 收录的协议与数据面**：suggest 协议扩展形态；`create_task_from_message` 支持 done + completed_at + 跟进记录；回填来源标记字段；`pk context` 判重上下文是否纳入已完成任务及防 token 膨胀的裁剪策略。
2. **统计隔离口径**（产品口径，逐项决策）：连胜（按 completed_at 日期集合去重）、今日捕捉、图鉴累计 / 里程碑对回填任务的处理——排除、单列还是标注呈现。
3. **回填拉取工程面**：独立游标 / 断点续跑、并发与限速、进度可视、与增量轮询的互斥、会话过滤偏好是否沿用。
4. **聚合判定面**：事件簇聚合粒度、跨会话同一事项的处理、「生命周期判定」prompt 规则、置信度分级与低置信呈现。
5. **报告与收录交互**：入口位置（收音机 vs 图鉴 / 复盘侧）、报告信息架构、逐项收录 / 忽略 / 拆并操作、报告留存与再生成。
6. **增量场景顺带收益的取舍**：实时消息里「这事已搞定」是否也获得「建议完成既有待办」出口——本次顺带 or 明确不做。
7. **成本与时长护栏**：触发前的预估展示、可中止、分批续跑的粒度。

### 待用户确认项（就地决策 + 待确认标记，随批量关卡带回）

- 回顾时间范围上限与默认值（倾向：默认 3 个月、上限 6 个月）。
- 报告载体（倾向：应用内页为主，Markdown 导出复用现有导出管线）。
- 统计隔离口径（倾向：回填任务进图鉴累计但标注来源；连胜与里程碑排除回填日期）。
