# editable-prompts 方向性设计记录（brainstorming）

> 纪律声明：本会话可用技能列表无 `brainstorming`（宿主侧软链分发未覆盖本 ZCode 会话），
> 按 `~/.zcode/AGENTS.md`「brainstorming 覆盖规则」手动执行同等纪律——只做需求探索 +
> 方案选型，章节限定为①问题理解②关键约束③方案探索④待落地清单。
> 规模分级：**L**（跨前端 Vue 与 Rust 后端、新增「提示词覆盖」实体、新设置 UI、
> 涉及占位符协议与注入隔离安全语义）。

## ① 问题理解

**要解决什么**：应用的 5 处 AI 功能提示词全部硬编码在 Rust 源码里，用户想调整判定
口径（例如放宽待办提取倾向、改桌宠说话风格、调整标签治理规则）必须改代码重新编译。
希望提供应用内的查看与编辑能力，让提示词成为用户可运营的配置。

**现状盘点（5 处硬编码）**：

| # | 功能 | 位置 | 动态部分（代码拼接，非提示词本体） |
|---|------|------|----------------------------------|
| 1 | IM 分类（收音机判定待办） | `src-tauri/src/ai/prompts.rs` `TOOLS_SYSTEM_PROMPT` | `<AGENT_ID>` 占位符替换；消息列表正文由 `render_messages` 追加 |
| 2 | 快速捕捉（手动输入待办的结构化判定） | 同上 `CAPTURE_SYSTEM_PROMPT` | 同上 |
| 3 | 桌宠 AI 对话（F2 单轮问答） | `src-tauri/src/commands/pet.rs:136` | 任务快照 `{ctx}` 与提问 `{q}` 在 format! 里拼接 |
| 4 | 标签治理（词表近义合并复核） | `src-tauri/src/commands/tag_health.rs:225` | 词表与候选对列表追加在提示词之后 |
| 5 | 待办派发（把待办交给 agent 执行） | `src-tauri/src/commands/dispatch/prompt.rs` | **注入隔离定界块**（DATA_BEGIN/END laundering）+ `{task_id}`——安全结构 |

**谁**：应用的唯一用户（本机单用户桌面应用，无多租户）。

**为什么**：提示词是 AI 判定行为的「策略层」，与代码逻辑（协议、出口、安全）天然
分层；策略层改一次就重新编译不可持续。且调试判定效果时需要快速试错。

**success criteria**：
- 用户能在设置页查看每个 AI 功能**当前生效**的系统提示词（区分「内置默认」与「自定义」两种状态）
- 能编辑并保存，之后该功能调用即用新提示词，无需重启或重编译
- 能一键恢复内置默认
- 内置默认仍以编译常量为单源（现有 prompt 内容断言测试不失效），用户副本只是覆盖
- 不破坏 5 处调用链的动态拼接语义（占位符 / 追加正文 / 定界块）

## ② 关键约束

1. **占位符协议**：分类/捕捉提示词含 `<AGENT_ID>`（替换为 agent id）；桌宠对话的
   上下文与提问、标签治理的词表、派发的待办数据块都由代码拼接。用户编辑必须保证
   动态注入点不被破坏——占位符缺失时 agent 收不到关键信息（如 agent id，pk 侧
   记录建议来源会失效）。
2. **注入隔离安全语义（派发提示词特有）**：不可信 IM 正文经定界块包裹 + laundering
   防伪造边界逃逸。提示词本体一旦全文开放编辑，用户可能删掉「数据非指令」声明或
   定界块结构，削弱隔离。**方向性红线：定界块机制与数据声明保持代码控制**。
3. **测试锚点**：`prompts.rs` / `dispatch/prompt.rs` 的现有单测直接断言默认提示词
   内容（规则完整性回归）。默认值必须继续可编程断言。
4. **默认值演进**：应用升级会改进内置默认提示词；已保存的用户副本会与新版默认
   脱锚。需要明确语义（覆盖优先 vs 提示漂移），不能静默错乱。
5. **存储体系**：settings 表 KV 是现成的配置单源（`ai_agents` 已有 JSON-in-KV 先例），
   SQLite 迁移只追加不修改（红线）。
6. **单用户本地应用**：无并发编辑冲突、无权限模型；但提示词较长（分类提示词
   ~2000 字），编辑器 UX 需按长文本设计（textarea 而非单行输入）。
7. **坏输入兜底**：用户可能存入空串、破坏 JSON 语义边界（如派发数据块）或超长文本
   ——加载侧必须有「坏覆盖回落内置默认」的兜底，坏配置不能让判定管道挂死。

## ③ 方案探索

### 方案 A：settings KV 覆盖 + 设置页内嵌编辑器（推荐）

每个功能一个设置键存「覆盖文本」，空/缺省 = 用编译内置默认；设置页 Agent 分区
新增「提示词」卡：每个功能一块可折叠的查看 + textarea 编辑 + 恢复默认。

- **优点**：与现有设置体系完全同构（`ai_agents` 先例、SETTING_DEFAULTS/KEYS 协议、
  保存链路现成）；默认值单源仍在代码（测试锚点不丢）；UI 与其他配置一处运营；
  空值回落机制天然处理「恢复默认」与坏数据兜底。
- **缺点**：长文本在 settings KV 里编辑体验一般（但单用户低频操作可接受）；
  不支持外部编辑器 / git 版本管理。
- **派发提示词处理**：定界块结构代码控制不可编辑；至多开放「要求」段的自定义追加
  （是否开放及其粒度 → 留 SDD/AD 细化，方向性建议一期只读展示 + 不开放编辑）。

### 方案 B：文件系统模板（workspace 下 prompt 文件 + 打开目录入口）

提示词落 `~/.choose-you/prompts/*.md`，应用读取加载；设置页只提供「打开目录」。

- **优点**：高级用户可用任意编辑器、可 git 管理；提示词天然是文本文件的心智。
- **缺点**：与设置页割裂，普通用户不可发现；无 UI 校验与恢复默认引导；引入第二套
  配置加载机制（文件监听/损坏回落）与 settings 单源并立，架构复杂度上升；
  桌宠窗口/沙箱场景下目录路径暴露面变大。
- **适用前提**：若未来提示词要长文迭代、diff、团队共享，B 更合适；当前诉求是
  「应用内查看 + 编辑」，A 已覆盖。

### 方案 C：按 agent 粒度的提示词覆盖（每 agent 独立变体）

在 AgentConfig 上挂提示词覆盖，同功能不同 agent 可用不同提示词。

- **优点**：极端灵活（如 claude 与 pi 提示词微调差异）。
- **缺点**：N agents × M prompts 的组合爆炸；现状提示词与 agent 类型无关（统一走
  pk 协议），无实际需求支撑；编辑与状态管理复杂度大增。
- **结论**：过度设计，不推荐（若未来有真实需求可在此架构上演进）。

**推荐：方案 A**。与现有体系同构、默认单源保住测试锚点、覆盖语义清晰
（空 = 默认）；B 的优势场景（外部编辑/版本管理）当前不是诉求，C 无需求支撑。

### 伴随的方向性取舍（随方案 A 成立）

- **生效语义**：覆盖保存后**下一次调用**即生效（判定管道每次从 settings 读），
  不做热重载广播——与 `ai_agents` 配置生效语义一致。
- **默认漂移处理**：一期不做「默认已升级」提示（需版本戳与对比 UI，成本高）；
  恢复默认 = 清空覆盖回到编译默认。是否需要漂移提示 → 待落地清单。
- **桌宠对话占位符**：现以 format! 直拼 `{ctx}`/`{q}`，开放编辑需改为显式占位符
  协议（如 `{context}`/`{question}` 文本占位）——属于 AD 层契约决策，方向上
  统一「系统提示词 + 代码替换占位符」模型。

## ④ 待落地清单（交给 SDD / AD 的开放项）

1. **[SDD] 编辑范围**：5 处提示词哪些开放编辑？（方向性建议：1-4 开放，
   5 派发只读展示不开放）——需要明确的用户故事与验收边界。
2. **[SDD] 占位符保护的用户契约**：编辑器是否阻止缺少必要占位符的保存？
   还是仅警告？（影响验收 Gherkin 的写法）
3. **[SDD] 恢复默认的交互语义**：确认「清空覆盖」还是「显式按钮 + 二次确认」。
4. **[AD] 存储契约**：设置键命名（如 `ai_prompt_*` 前缀）、每键语义（空串 vs 缺失）、
   加载侧兜底（坏覆盖回落默认）的具体机制与错误路径。
5. **[AD] 后端加载层**：5 处调用点改造为「读覆盖 → 回落编译默认」的统一入口
   （prompts.rs 现有 `build_*` 签名如何演进、getter 闭包如何传入 judge/pet/tag_health
   /dispatch 各调用链）。
6. **[AD] 桌宠对话占位符改造**：format! 直拼改显式占位符协议的兼容性（无覆盖时
   行为逐字节不变）。
7. **[UIUX] 编辑器形态**：设置页内的布局（折叠面板？每功能一卡？）、长文本编辑
   控件、默认/自定义状态标识、恢复默认入口、占位符提示的位置与文案。
8. **[UIUX] 三语言 i18n 文案**（zh-Hans / zh-Hant / en）。
9. **[SDD/AD] 长度上限与校验**：是否设上限（防误粘贴超大文本入库）。
